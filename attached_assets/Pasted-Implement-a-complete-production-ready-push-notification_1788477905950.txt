Implement a complete production-ready push notification system for the CocheTalk.NG mobile app.

IMPORTANT: Do not redesign the existing UI or break existing functionality. First inspect the existing codebase, authentication, database structure, user roles, notification-related components, and API architecture. Reuse the existing architecture where possible.

## 1. Push Notification Infrastructure

Implement real push notifications for the Expo/React Native Android application.

Use an appropriate production-ready Expo push notification architecture.

The system must:

* Register each user's device for push notifications after login.
* Store the user's push notification token securely in the backend/database.
* Support Android push notifications when the app is:

  * Open
  * In the background
  * Completely closed
* Handle notification permissions correctly.
* Handle invalid/expired push tokens.
* Prevent duplicate device tokens.
* Allow a user to have multiple devices.
* Remove/deactivate tokens when appropriate.
* Never expose server-side secrets or API keys in the mobile application.

Do not use AsyncStorage as the source of truth for notification preferences or notification permissions. Local storage may only be used for appropriate device-level caching.

---

# 2. Notification Categories

Create separate notification settings for the following categories:

1. New Answers

   * Notify a user when someone answers their question.

2. Comments & Replies

   * Notify a user when someone comments on or replies to their content.

3. New Messages

   * Notify a user when they receive a new message.

4. Marketplace Updates

   * Notify users about relevant marketplace activity, such as listing approval/rejection or important listing updates.

5. Provider Updates

   * Notify service providers about relevant account/provider activity, such as verification status.

6. Announcements

   * Allow administrators to send important platform-wide announcements.

7. System Notifications

   * Important security/account/system notifications.
   * These should not be treated as ordinary marketing notifications.

Keep the notification categories configurable so additional categories can be added later without restructuring the entire system.

# 4. Admin Global Notification Controls

Example:

GLOBAL NOTIFICATION SETTINGS

New Answers                    ON
Comments & Replies             ON
New Messages                   ON
Marketplace Updates            ON
Provider Updates               ON
Announcements                  ON
System Notifications           ON

Each setting should have an ON/OFF control.

The Admin setting represents the GLOBAL availability of that notification category.

---

# 5. IMPORTANT: Admin Setting Overrides User Setting

Implement the following hierarchy:

ADMIN GLOBAL SETTING
↓
USER NOTIFICATION SETTING
↓
SEND NOTIFICATION

The Admin setting always takes priority.

### Scenario 1 — Admin ON

If:

Admin = ON
User = ON

→ Send notification.

If:

Admin = ON
User = OFF

→ Do NOT send notification.

The user is allowed to turn the notification back ON.

---

### Scenario 2 — Admin OFF

If:

Admin = OFF
User = ON

→ Do NOT send notification.

If:

Admin = OFF
User = OFF

→ Do NOT send notification.

The user MUST NOT be able to turn the notification ON while the Admin has globally disabled it.

---

# 6. User Interface Behaviour When Admin Disables a Category

If the Admin disables a notification category globally, reflect this clearly in the user's Settings → Notifications screen.

For example:

New Answers
[ OFF / DISABLED ]

"Disabled by CocheTalk administrators"

The toggle should be disabled/locked.

The user must not be able to override the Admin setting.

Do not simply hide the setting from the user. Prefer showing the setting as disabled so the user understands why they cannot enable it.

Example:

New Answers                 🔒 OFF
Disabled by administrator

Comments & Replies          ON

New Messages                ON

---

# 7. If Admin Re-enables a Category

When the Admin changes:

New Answers = OFF

to:

New Answers = ON

the notification category becomes available to users again.

However, respect the user's previously selected preference.

Example:

Before Admin disabled it:

User preference = OFF

Admin = OFF

After Admin changes to:

Admin = ON

The user's setting should remain:

User = OFF

Therefore:

→ Do not send notifications until the user chooses ON.

Do NOT automatically change the user's personal preference when the Admin temporarily disables a category.

This preserves the user's preference.

---

# 8. Effective Notification Logic

Every notification must pass through a centralized notification service/function before being sent.

Create a single source of truth for this logic.

Conceptually:

canSendNotification(user, notificationType)

should check:

1. Does the notification category exist?
2. Is the Admin global setting enabled?
3. Is the user's personal setting enabled?
4. Does the user have a valid push token?
5. Does the notification meet any required business rules?

Only then send the notification.

The logic must be enforced SERVER-SIDE.

Do not rely on frontend toggles to enforce notification restrictions.

# 11. Notification Triggers

Connect notifications to actual CocheTalk events.

Implement at minimum:

### Forum

When User A answers User B's question:

→ User B receives "New Answer" notification.

When someone comments/replies:

→ Relevant user receives "Comments & Replies" notification.

Do not notify users about their own actions.

---

### Messaging

When User A sends a message to User B:

→ User B receives "New Message" notification.

Do not send a notification to the sender for their own message.

---

### Marketplace

When Admin approves/rejects a listing:

→ Seller receives "Marketplace Update".

When an important marketplace event occurs:

→ Send the appropriate marketplace notification.

---

### Provider

When a provider's verification status changes:

→ Notify the provider.

---

### Announcements

Allow Admin to create a platform-wide announcement.

The Admin should be able to select:

* Notification title
* Notification message
* Optional destination/screen
* Optional audience if supported

Announcements must respect the global Announcement setting and the user's Announcement preference.

# 16. Permission Handling

When a user logs into the Android app:

1. Check notification permission.
2. Request permission where appropriate.
3. Register the device push token.
4. Store/update the token on the backend.
5. Respect the user's device-level notification permission.
6. Respect Admin global settings.
7. Respect the user's individual notification settings.

Important:

Device notification permission is separate from CocheTalk notification preferences.

The notification can only be sent when BOTH the device/app permission and the effective CocheTalk notification setting allow it.

---

# 17. Error Handling

Handle:

* Notification permission denied
* Invalid push token
* Expired push token
* User has no registered device
* Admin has disabled category
* User has disabled category
* Push service failure
* Network failure
* Duplicate notification
* App opened from notification
* Notification received while app is open

The app should fail gracefully without crashing.

---

# 18. Security

Do NOT allow a normal user to manipulate:

* Admin global notification settings
* Other users' preferences
* Other users' push tokens
* Notification records belonging to other users

Admin settings must be protected by backend role/permission checks.

Do not rely on hiding Admin UI elements as the security mechanism.

# 21. Final Acceptance Criteria

The feature is complete only when:

✓ New users have all applicable notification settings ON by default.

✓ Users can independently turn notification categories ON/OFF.

✓ Admin can globally disable any notification category.

✓ When Admin disables a category, users cannot re-enable it.

✓ Disabled categories are visibly shown as locked/disabled to users.

✓ Admin global settings are enforced server-side.

✓ Re-enabling a category does not overwrite the user's previous preference.

✓ Push notifications work when the app is open, backgrounded and closed.

✓ Notifications are stored in the backend.

✓ Users can view/read notifications inside the app.

✓ Multiple devices are supported.

✓ Invalid tokens are handled.

✓ No API secrets are exposed in the mobile app.

✓ Google/Facebook/Clerk authentication continues to work.

✓ Existing CocheTalk features are not broken.

✓ The feature is tested on a real Android production/release build.

Before making major architectural changes, inspect the existing codebase and explain what you intend to reuse versus what needs to be added. Do not unnecessarily introduce a new backend technology if the existing backend/database architecture can support this feature.
